# Skills Baseline

## 1. 文档目标

本文件用于把当前项目后续要沉淀的 skills 做成一个可追踪、可比较、可迭代的基线。

适用范围：

- 语法风格类
- 代码仓骨架类
- 代码迁移类
- DT 测试类
- DFX 类

使用原则：

- 一个版本只维护一份总表，不为每个 skill 单独再开基线文档
- 每次迭代先更新总表，再补充版本记录
- skill 是否进入基线，以“可复用、可验证、可交付”为准

## 2. 版本规则

建议使用以下字段统一追踪：

- 基线版本：`SB-YYYY.MM`，例如 `SB-2026.03`
- 状态：`Proposed` / `Planned` / `In Progress` / `Baselined` / `Deprecated`
- 成熟度：`L0` 到 `L4`
- 优先级：`P0` / `P1` / `P2`

成熟度定义：

| 等级 | 定义 |
| --- | --- |
| L0 | 只有问题识别，没有形成 skill 方案 |
| L1 | 已有 skill 草案，触发条件和边界初步明确 |
| L2 | 已能在项目里落地使用，但稳定性或覆盖面不足 |
| L3 | 已成为团队默认做法，可支撑版本交付 |
| L4 | 已标准化，可复用到相似项目或后续仓库 |

## 6. 每次版本更新动作

建议固定按这 6 步更新：

1. 回看上一版本的总表，确认哪些 skill 状态变化了。
2. 用本次穿刺结果更新“当前穿刺结论”和“主要缺口/风险”两列。
3. 把成熟度按 `L0-L4` 调整，不要只改状态不改成熟度。
4. 如果 skill 已可复用，就补齐“验收标准”和“依赖输入”。
5. 在“版本迭代记录”里追加一行，说明本次新增、升级、下线。
6. 对没有变化的 skill 不改描述，只改目标版本或风险即可。

## 7. 推荐的后续拆分方式

当这份基线稳定后，再按下面方式拆分细文档：

- `docs/skill-baseline.md`
  - 只保留总表、版本记录、状态定义
- `docs/skills/style/`
  - 放语法风格类的细规则
- `docs/skills/scaffold/`
  - 放代码仓骨架模板
- `docs/skills/migration/`
  - 放迁移映射表、迁移 playbook
- `docs/skills/dt/`
  - 放回归矩阵、测试计划
- `docs/skills/dfx/`
  - 放日志规范、故障分析模板

这样后续版本迭代时，管理入口只有一个，展开内容再按类别细化。
